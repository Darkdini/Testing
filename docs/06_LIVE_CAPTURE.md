# Живой протокол (Android-клиент) — по захвату трафика

Игра жива. Захват реальной сессии Android-клиента (`Client version 2.0.112`)
показал **актуальный протокол** — он другой, чем старый J2ME-FLAP. Разбор делает
`tools/parse_capture.py`.

> В примерах ниже личные данные (логин/пароль/почта/uid устройства) заменены
> плейсхолдерами. Сам файл захвата в репозиторий не кладём (в нём твои креды).

## Формат лога захвата

```
<O|I> <длина> <hex>
O = клиент -> сервер,  I = сервер -> клиент
```
Каждая строка — один вызов read/write (сервер часто шлёт по 1 байту, потом тело).

## Транспорт и рамки

- Обычный TCP. В начале сессии — обмен магией `38 0f` (клиент шлёт, сервер
  эхо-отвечает `38 0f`).
- Дальше — сообщения. У каждого сообщения заголовок вида:
  ```
  [len:2] [seq/flags...] 80 80 80 [context/id ...] <токены>
  ```
  Сигнатура `80 80 80` отделяет заголовок-маршрутизацию от полезных данных.
  В контексте встречаются 6-байтовые идентификаторы объектов
  (напр. `2e2495 6f7c24`, `5215xxxxxx`, `5371xxxx`) — это сущности игры
  (здания/тайлы/игроки).

## Токены данных (маркер `0x66`)

Полезная нагрузка — поток типизированных токенов:

| Байты | Тип | Формат |
|-------|-----|--------|
| `66 39` | строка | `[0x80\|len]` затем `len*2` байт **UTF-16BE** |
| `66 09` | int32 | 4 байта big-endian (значение) |
| `66 17` | int32 | 4 байта big-endian (id/счётчик) |
| `66 31` | int8 | 1 байт (флаг/маленькое число) |
| `66 0f` | oid | 8 байт — идентификатор объекта (long) |
| `66 3b/29/93/cb/e3 …` | прочее | доснять по захвату |

Строки — **UTF-16BE** (не CP1251, как в старом клиенте).

## Сценарий логина (из захвата)

```
#000 C->S  38 0f                       — connect magic
#001 S->C  38 0f                       — сервер эхо
#003 C->S  "Android | Client version 2.0.112"
           "Xiaomi  |  2306EPN60G  |  15"    (бренд|модель|версия ОС)
           1220, 2576                        (параметры/разрешение)
#006 S->C  строка "socket://<host>:5005"     — РЕДИРЕКТ на игровой сервер
           (auth-сервер отдаёт адрес игрового узла — как в OSCAR)
#009..15 S->C  объекты состояния (oid + значения) — стартовая подгрузка
#016 C->S  <login>, <password>, "<email>", "none",
           {"instid":"PDA_LIFE","brand":"Xiaomi","model":"...",
            "uid":"<device-uid>","accounts":["<email>"]}   — регистрация
#019.. S->C  большие кадры мира/карты/UI (видны строки "Load",
             "background.", координаты, id зданий)
```

Ключевые выводы:
- **Есть редирект**: первый сервер — авторизация, он присылает `socket://host:5005`,
  дальше клиент играет уже с игровым узлом. При написании своего сервера это надо
  повторить (или сразу отдавать свой адрес).
- **Устройство идентифицируется** JSON-ом с `uid` (аналог старого RMS-ID).
- **UI и мир** приходят с сервера (строки ресурсов/фонов внутри кадров) — как и в
  старом клиенте, логика на сервере.

## Как снять свой захват

1. Прокси/сниффер между Android-клиентом и сервером:
   - `mitmproxy --mode transparent` / `tcpdump` на устройстве с root, или
   - Android-VPN-снифферы (PCAPdroid) — пишут per-app TCP в pcap/лог.
2. Сохранить в формате `<O|I> <len> <hex>` (или конвертировать pcap).
3. Прогнать через парсер:
   ```bash
   python3 tools/parse_capture.py capture.log --limit 80   # транскрипт
   python3 tools/parse_capture.py capture.log --strings     # только тексты
   ```
4. Каждую пару «запрос C->S ↔ ответ S->C» записывать как команду — так набирается
   спецификация, по которой пишется сервер.
