# Как «отснифать» ответы сервера

**ОБНОВЛЕНО: сервер ЖИВ.** Игра существует и обслуживается в современном
Android-клиенте (`Client version 2.0.112`). Живой захват трафика подтвердил это
и позволил декодировать актуальный протокол — см. `docs/06_LIVE_CAPTURE.md` и
`tools/parse_capture.py`. То есть классический сниф РАБОТАЕТ: снимаешь трафик
своего клиента и видишь и запросы, и ответы сервера.

> Ремарка про старый J2ME-клиент (этот JAR): он ходил на `mmog1.com:2500`
> по протоколу FLAP. Сегодня `mmog1.com` резолвится в чужой IP, а порт 2500 не
> отвечает — старый вход мёртв. Но сама игра переехала на новый протокол
> (Android), который и виден в захвате. Ниже — три пути; для живой игры основной
> путь — именно сниф (п.2).

---

## 1. Статический сниф — читаем ПАРСЕР клиента (главный метод)

Клиент сам разбирает каждый серверный пакет. Значит его код-приёмник **точно
описывает** формат ответа: сколько байт, в каком порядке, что значат. Это
надёжнее любого снифа — ты видишь ВСЕ ветки, даже редкие.

Путь приёма в клиенте:

```
ar.run()  — поток-приёмник, читает кадры FLAP
   └─ ar.h() -> ae.a(bytes)         — распарсить кадр
        ├─ канал 1/4 -> k (логин/сессия): k.c(f) handshake, k.a(f) ответы логина
        └─ канал 2   -> p.e(f)  — ГЛАВНЫЙ роутер игровых пакетов:
              group 10 -> p.p(f)   замок/здания, subtype 0..20
              group 11 -> p.n(f)   subtype 4..7
              group 12 -> p.i(f)
```

Инструмент — `server/disasm.sh`:

```bash
mkdir -p out && (cd out && unzip -o ../*.jar >/dev/null)   # один раз
server/disasm.sh out p e      # главный роутер: по каким group/subtype что
server/disasm.sh out p p      # разбор пакетов замка (group 10)
server/disasm.sh out k a      # разбор ответов логина
```

Как читать байткод парсера (соответствие «опкод → формат ответа»):

| В байткоде видишь | Значит сервер прислал |
|-------------------|-----------------------|
| `Method t.b:([BI)I` | 1 байт (unsigned) |
| `Method t.c:([BI)I` | 2 байта big-endian (short) |
| `Method t.a:([BI)J` | 4 байта big-endian (int/long) |
| `Method t.b:([BII)` | строку CP1251 (offset, length) |
| `Method aj.a:([BI)` | TLV: `[тип2][длина2][значение]` |
| `putfield … :J/:I` | куда легло значение (ресурс, счётчик…) |
| `tableswitch/lookupswitch` | ветвление по subtype/типу элемента |

Пример: в `p.p(f)` первый же `f.a()` + `tableswitch {0..20}` = сервер в поле
`subtype` шлёт номер операции замка (0..20), а дальше каждая ветка читает свой
формат. Разбирая ветку за веткой, получаешь точную спецификацию ответа.

## 2. Живой сниф ЗАПРОСОВ клиента (что он спрашивает)

Ответы снять негде, но **запросы** клиента снять легко — направь клиент на свой
сервер (`server/mock_server.py`), он логирует каждый входящий пакет с hex-дампом
и разбором TLV. Так узнаёшь вторую половину: какие команды и с какими
параметрами клиент шлёт (см. `docs/04_HOW_TO_REBUILD.md`, «петля восстановления»).

Связка «парсер (п.1) + лог запросов (п.2)» полностью заменяет классический сниф:
- из парсера знаешь формат ОТВЕТА,
- из лога знаешь формат ЗАПРОСА.

Если хочется именно Wireshark-картинки — поставь клиент за локальный
TCP-прокси/`mitmproxy --mode raw` на 2500 и смотри байты; но «сервером» всё равно
будет твой `mock_server.py`.

## 3. Внешние источники (если нужна ТОЧНАЯ копия оригинала)

Формат ты восстановишь из клиента, а вот конкретные ЧИСЛА оригинального баланса
(стоимости, тайминги) в клиенте не зашиты. Их источники, если цель — точная копия:

- старые дампы трафика/логи серверов в фан-сообществах игры;
- вики/форумы/скриншоты игроков (значения стоимостей, времени, характеристик);
- память тех, кто играл.

Если цель — свой сервер (рекомендуемый путь B), числа придумываешь сам, а формат
берёшь из клиента.

## Что уже разведано (заготовка таблицы команд)

Заполняй по мере разбора (`server/disasm.sh` + лог запросов):

| Напр. | group | subtype | Кто в клиенте | Смысл |
|------:|------:|--------:|---------------|-------|
| C→S | 1 | 0 | k.c(f) | версия клиента + размер экрана |
| C→S | 4 | 12 | k | ID устройства |
| C→S | 4 | 5 | k.c() | логин + пароль (TLV) |
| S→C | 4 | 5 | k.a(f) | выданный ID |
| S→C | 4 | 0 | k.a(f) | логин OK |
| C→S | 10 | 3/1 | p.i() | запрос времени постройки |
| S→C | 10 | 0..20 | p.p(f) | операции замка (разобрать по веткам) |
| S→C | 11 | 4..7 | p.n(f) | (разобрать) |
| S→C | 12 | — | p.i(f) | (разобрать) |
